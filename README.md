<p align="center">A terminal workspace for coding agents: projects, tasks, notes, live agent panes, their turns and your reviews, gathered in one TUI.</p>

<p align="center"><img alt="mtm over invented data with three scripted demo agents (not real ones): pinning a project, then the Inbox: one agent in Needs you, one finished, one in Working, each border in its state colour; a finished agent's turns with its edits as diffs; answering the waiting agent live, which moves it to Working" src="assets/demo.gif" width="720"></p>

Matomeru (`mtm`) is built on [ochazuke](https://github.com/unixsuperhero/ochazuke) and runs its agents in panes of a [TUIOS](https://github.com/Gaurav-Gosain/tuios) daemon it starts for itself. Every action in the TUI is also a command: `mtm task new --title ...`, `mtm project pin`, `mtm catalog`.

The Inbox page (`I` from anywhere) is what needs you: action items from any source, unread first, with the count of unread and open items in the title row (`inbox 2/5`). `enter` opens an item's URL, `u` marks it read or unread, `s` snoozes it, `x` archives and `X` restores it, `t` and `c` promote it to a todo or a task, `m` moves it to a project and `d d` deletes it. Tools push items in through one command, idempotent on the source and `--key` (else the source and `--url`), so a poll that runs again refreshes its row:

```sh
mtm action-item add --source gh --url https://github.com/o/r/pull/7 --why "review requested" --title "Fix the store" --dir ~/proj/r
```

It prints the item as JSON (`id`, `new`, `state`, …). An item needs nothing: one with no project, task or pane is unassociated. `mtm action-item list`, `count`, `show`, `read`, `snooze --for 4h`, `archive`, `restore`, `promote-task`, `associate --task ID` and `delete` are the rest.

mtm's own panes feed the inbox too, while the TUI is open: an agent that waits for your input, a finished turn and an errored agent each become an item (source `mtm`, kind `needs-input`, `done` or `errored`), owned by the pane's task or project. A needs-input or errored item is archived once the pane moves on; a done item is marked read once you attach the pane. The settings `inbox.signal.needs-input`, `inbox.signal.done` and `inbox.signal.errored` turn each kind off.

A terminal pane's finished commands feed it as well (kind `command`), from the OSC 133 marks a shell sends to tuios. `inbox.terminal-commands` says which: `off`, `failed` (exit status not 0), `long` (the default: failed, or ran at least `inbox.terminal-commands.long-minutes`, default 10) or `all`. A command that runs a program in `inbox.terminal-commands.ignore` (vim, less, ssh, top and other interactive ones, and the agent CLIs claude, codex, omp, opencode, aider, gemini and mtm itself) never raises. The item reads like "`go test ./...` exited 1 after 12m"; a failed one puts the pane in the queue as errored and is archived once a later command there succeeds or you attach the pane, and a long one is marked read when you attach it. Each command raises once (keyed by window, daemon start and command number), whichever TUI sees it; commands that finished before mtm started are not raised.

The Inbox page (id `panes`) draws the queue as a bordered "Needs you" panel at the top, Working as a bordered panel on the column's last lines, and the panes list in the lines between (`panes.layout panels`, the default; `stacked` is the earlier three titled lists sized by `panes.section-layout`). A panel is `panes.panel-min` lines tall at least (default 6, border included), grows with its rows up to `panes.panel-max` (default 10) and then scrolls, its title saying how many rows it hides; an empty one keeps its lines and says so (`panes.empty-panels show`, the default, so the column does not jump when the first item arrives) or gives them to the panes list (`hide`). The lists are focus stops in drawing order (`j`/`k` spill across them) and a focused panel draws the accent border. `g n`, `g w` and `g p` move the focus to Needs you, Working and the panes list (`panes.focus-section queue|working|panes`); `W` still steps through the panes that need input. Which agent states put a pane in Working, the queue or the errored category are the lists `panes.working-states` (default `working`), `panes.waiting-states` (`needs_input`) and `panes.errored-states` (`errored`), tuios's words; add another word (for example OSC 7501's `blocked`) to any of them. A row moves to its new list as soon as its pane changes state, the cursor with it; `panes.sticky-rows` (default off) keeps the row under the cursor in its list until the cursor moves off it, and `panes.stable-order` (default on) keeps each row's place in its list until it leaves.

Schedules run the outside signal producers on an interval, while the TUI is open, so their items arrive without a key press. The built-ins are `gh-signals` (`o-gh signals`, every 5m, `auto`: on where `o-gh` is installed and `gh auth status --active` passes) and `slack-signals` (`o-slack signals`, every 5m, off; it belongs to the work machine, and elsewhere turning it on only records "missing" on its row). One setting flips each: `mtm settings set schedule.gh-signals.enabled on|off|auto`, and `schedule.NAME.interval` sets how often. `<config>/schedules.json`, a JSON array like `harnesses.json`, adds schedules or changes a built-in's command (`[{"name": "todo-sync", "command": ["o-todo", "sync"], "interval": "1h"}]`). `S` on the Inbox opens the Schedules page: `r` runs the selected schedule now, `e` turns it on or off, `i` sets its interval, and the detail shows its recent runs and output. Runs go under `nice`, never overlap (two open TUIs run each occurrence once), time out after 2m (`"timeout"` in the file), back off after failures (the interval doubled per failure, at most an hour) and say a first failure as a notice. `mtm schedule list`, `show`, `history`, `run-now`, `enable`, `disable`, `toggle`, `set-interval --interval 10m` and `reset` are the CLI.

Schedules can also run prompts. `mtm schedule add --prompt "summarise overnight PRs" --when "weekdays 8:30" --harness claude --model sonnet --effort high --permission-mode plan --project matomeru` stores a row (on when it has a time, else off) that starts an agent at each time: an ordinary agent pane in the project's session, named after the schedule, linked to `--task` when given. `--into pane --pane reviewer` queues the prompt in the open pane named `reviewer` instead (tuios types it when the agent rests, never over a question; with no such pane a run starts one). `--when` takes `every 30m`, `daily 09:00`, `mon,wed,fri 09:00,17:30`, `weekdays 8:30`, `cron 0 9 * * 1-5` or `never`; `--start 2026-11-01` and `--end 2026-12-31` bound it. Runs missed while mtm was closed are skipped (`schedules.catch-up none`) or run once on start (`once`; a row's `--catch-up` wins). `schedule edit NAME --field value`, `duplicate NAME [--as NEW]` and `delete NAME` change the stored rows; editing a built-in stores a copy. On the Schedules page `n` adds a row and opens its form, `E` edits one, `d d` deletes a stored one; the form writes each change as you type. Each run's history says what it launched and links its pane.

How a program runs is data, its `drive`: `terminal` (a tuios pane with an emulator, the default for harnesses and shells), `exec` (a plain process whose stdout and stderr stream into a job and whose exit code is the outcome, with no pane and no emulator; the default for schedules' command rows) or `api` (reserved for the API pane: accepted in files, refused as "not available yet" when used). A harness profile sets it (`harnesses.json`: `{"name": "claude", "drive": "exec"}` runs claude's argv as a process, the prompt on stdin, or last for `"prompt": "arg"`), as does a schedule's command row (`"drive": "terminal"` opens a pane running the command each run). A run overrides it: `mtm agent start --drive exec`, `project launch --drive …`, `schedule run-now NAME --drive terminal`. `command run "go test ./..."` from the palette or the CLI runs a command line (`sh -c`) with `--drive exec` (default), `terminal` or `api`, in `--dir` (default: the pinned project's directory, else home). The Runs page (after Schedules) lists this TUI's exec runs, newest first, with their state and exit code; its detail streams the output while the run goes. `r` reruns, `d d` forgets, `run.stop` stops one (its process group is killed), `run.list` and `run.show` are the CLI. The jobs ticker shows each run by its title while it runs.

Where the Panes detail opens a pane is its view: `turns` (the Turns tab), `terminal` (the live Screen) or `both` (the Turns tab with the pane's screen beside it). It comes from the pane's own view (`pane.view turns|terminal|both [--split N]`, from the palette or the CLI; `pane.view default` drops it), else the harness profile (`"view": {"open": "both", "split": 60}` in `harnesses.json`, merged by field over a built-in's, `null` removes it), else the settings `agent.view` (default `turns`, today's layout) and `agent.view-split` (default 50, the percent of the width the turns take, 10..90). The split draws only when some row chooses `both`. The tab you pick stays while the selection moves between panes of one view; a pane whose view differs opens on its own. No key is bound by default (`v` is free on pane rows; bind it in `bindings.json`, e.g. `pane.view` with `{"view": "both"}`).

An agent pane's running subagents are rows under its row in the pane list, wherever the row is (the Panes tree under its session, Needs you, Working): the subagent's description and type, its status word in its class's colour and its age. A row leaves when the subagent finishes; one that fails or is killed stays `panes.subagents-linger` (default 30s) and then leaves, so the end is seen. The rows come from the pane's session log, found as the Turns tab finds it (the harness's own record first, so a pane attached to a Claude background session with a stale id still has its rows) and read in the format its harness names (`harnesses.json` `"log"`: `claude` for the built-in claude, `omp` for omp, none for codex; a harness with no format, or one whose log names no subagents, has no rows): a Claude pane's Agent and Task calls and their task notifications, read off the loop from where the last read stopped. A background subagent shows whatever its pane's state, and one that stopped "waiting on its own background work" still runs until its task notifies again; a foreground one shows while its pane's agent works. j and k pass through them; a selected one shows its pane's detail; `enter` (`pane-child.open`) shows the pane's Turns tab with the card of the call that started the subagent selected, the focus left on the list; `y` (`pane-child.copy`) copies its description, type and id. `panes.subagents off` takes the rows away and stops the reads.

Turns cards draw their status word (a turn's, a task notification's) in one of four classes, from one table of words (`statusWords` in `cmd/mtm/turn_status.go`): needs you (`state.needs-input`), working (`state.working`), done (`state.done`: done, completed, finished, success, exit 0, stream ended) and bad (`state.errored`: failed, error, interrupted, killed, stopped, cancelled, a non-zero exit). A word in no row is muted. `turns.status-glyph` and `turns.status-border` (alert, all, off) turn the glyph and the border colour off; themes.json `tones` restyles the four.

The prompt box below a pane's Turns tab (and its Screen tab) writes to the pane; `enter` sends. After a send the box leaves insert mode for normal (`i` writes again); `prompt.after-submit-mode insert` keeps typing. Whether mtm asks for the pane's task or project after a send is `prompt.after-submit` (`pick-task`, the default, `pick-task-if-unassociated` or `none`); the picker gives the box back in the after-submit mode. `prompt.on-screen false` takes the box off the Screen tab, and the screen gets its rows; `prompt.on-terminals false` takes it from shells. Each pane has its own draft: the box shows the draft of the pane it writes to, so text typed for one pane stays that pane's (with its undo history and attached images) when the selection moves, and comes back with it; drafts last while mtm runs. `prompt.draft-per-target false` keeps one text across panes.

Tasks have saved prop filters on the Work tree and the tasks outline (`T`): `mine` matches `made-by=owner`, `agents` matches `made-by=agent`, and `all` includes unknown makers too. With a task list focused, `z ]` / `z [` cycle forward/backward; the filter strip shows the current name and conditions. `/` text search combines with them. The standard task list CLI accepts `--filter mine` (or `agents` / `all`) beside `--where`. User definitions in ochazuke's `list.filters` setting can add or override names. `list.filter-strip=false` hides the strip and `list.filter-cycle=false` disables cycling; both default on.

`work.tasks-filter` selects the Work page's startup saved filter (`all` by default); cycling stays local to the list for the session. An old `tasks.made-by` value is migrated once to that setting, preserving other settings. The old name remains a readable/writable deprecated alias for one release. `mine` now means the owner exactly; tasks with unknown makers appear in `all`. Notes use the same `mine` / `agents` / `all` saved filters on the Notes page and in the tasks outline. Every new note records its own `created-by` actor (owner, or agent with harness, pane, session, task and model); `made-by` is that actor's kind. CLI, MCP `task_note_add`, the editor and quick notes share this creation path. Older notes remain `unknown`; editing them does not claim them. Agents cannot change a note's maker.

The tasks outline shows the selected task's notes in a list beneath the task tree. `ctrl+w w` walks the panes. Vertical motion stays inside a modal list in ochazuke v0.65.0; a skipped story records the framework spill gap. Focus the notes to cycle their filters with `z ]` / `z [`; each list keeps its own filter through refreshes. Note rows keep their usual view, edit, move, rename, duplicate and delete actions. `notes.task-pane=false` hides the new pane (default `true`). The standard `note list --filter mine` (or `agents` / `all`) uses the same definitions; framework `list.filter-strip` and `list.filter-cycle` also apply to notes.

Compared with Vim:

| Vim form | Help tag | mtm |
|---|---|---|
| `:filter /pattern/ command` | `:filter` | Similar: restrict visible results; prop filters match typed record fields. |
| No counterpart | n/a | Named `mine` / `agents` / `all` definitions are app catalog data. |
| No counterpart | n/a | `z ]` / `z [` cycle named prop filters for tasks and notes; these keys are framework bindings. |
| `CTRL-W w` | `CTRL-W_w` | Same: move to the next pane, including the task's notes. |

A note has an optional title; an empty one shows the note's first line, as every note did before (the body is never the title). The note's verbs are ochazuke's standard ones over its props (`id`, `title`, `summary`, `text`, `project`, `task`, `made-by`, `created-by`, `created`, `updated`): `mtm note get|list|create|set|delete|watch|rename|move|duplicate`, for example `note rename --id ID --name Plans`, `note move --id ID --to matomeru` (`--to ""` unassociates) and `note set --id ID task=t1` (the task's project comes with it). `note new` and `note edit` keep their meaning (the owner inferred from the selection; no text opens the editor) and run `create` and `set` underneath, so `history.undo` reverts them. A standard `note create` fills `project` and `task` from the focused row and says so (`create.from-focus false` leaves them empty). On a note row `m` is `note.choose-move` (the project chooser), `d d` the standard delete. The editor shows the title above the body and starts on the body; `notes.title-field false` hides the title field. The quick note is body-only. `note.associate` is an old name of `note.move`, kept for one release.

A task's verbs are ochazuke's standard ones over its props (`id`, `title`, `status`, `project`, `parent`, `easy`, `snoozed-until`, and the read-only `position`, `created`, `updated`): `mtm task get|list|create|set|watch|rename|move|duplicate`, for example `task rename --id t1 --name "Write it"`, `task move --id t1 --to ochazuke` (`--to ""` unassociates; a move takes the task to its new project's top level, and its undo puts back both the project and the parent), `task set --id t1 parent=t2` (the parent's project comes with it) and `task set --id t1 status=active easy=true`. `task done ID` and `task status ID STATUS` are the standard set of `status` with their values preset; `task new` and `task edit` keep their meaning and run `create` and `set` underneath, so `history.undo` reverts them and `x`, `s` and `m`. On a task row `x` is `task.toggle`, `s` is `task.choose-status` (the status chooser; over a visual selection one choice sets every row) and `m` is `task.choose-move` (the project chooser). `task delete` is the standard delete: `d d` asks "Delete task ...?" with what the delete orphans (over a visual selection, `d` asks "Run task.delete on N rows?"), and `history.undo` puts the task back (what it orphaned stays orphaned); `task confirm-delete` is the same verb. `task.associate --project` is an old form of `task.move`, kept for one release; `task.associate --pane`, `--action-item` and `--context-item` relate those things to the task.

A project's verbs are ochazuke's standard ones over its props (`id`, `name`, `color`, `glyph`, `harness`, `preset`, `dir`, and the read-only `repo`, `origin`, `created`): `mtm project get|list|create|set|watch|rename|duplicate`, for example `project rename --id hub --name Hub`, `project set --id hub color=blue preset=fast` and `project create --name scratch --dir ~/tmp/scratch` (`dir` is attached as the default; the directory verbs change it after). A harness that is not registered is saved with a notice. `project new` and `project edit` keep their meaning and run `create` and `set` underneath, so `history.undo` reverts them; the editor's fields are the props'. A project has no owner, so no `move`. `project delete` is the standard delete (`d d` asks with what the delete orphans; `project confirm-delete` is the same verb); `pin`, `unpin`, `pick`, the directory verbs and `associate` (which relates a thing to the project).

A context item's verbs are ochazuke's standard ones over its props (`id`; `type` and `text`, written by `create` only; `project`, `task`, `starred`; and the read-only `session`, `window`, `pane`, `exists`, `created`, `seen`): `mtm context-item get|list|create|set|delete|watch|move|duplicate`, for example `context-item list --kind link` (or `--where type=link`), `context-item move ID --to hub`, `context-item set ID task=t1` (the task's project comes with it) and `context-item create --type link --text https://example.com`. `context-item forget ID` is the same as `delete` (the record only; what it names is untouched); `history.undo` puts a forgotten item back as it was. On a context row `*` stars (`context-item.star`, an alias of the standard set of `starred` with `toggle`; `--value true|false` sets instead; the old `--starred` still works until the next mtm release, with a one-time notice), `m` is `context-item.choose-move` (the project chooser) and `d d` asks "Forget ...?". `context-item add` still keeps every item found in a text and merges the ones already kept. `context-item.associate --task`, `--project` and `--scratch` are old forms of `set task` and `move`, kept for one release.

A pane's verbs are ochazuke's standard ones over its props (`id`, the window id or the row id `pane:SESSION/WINDOW`; `name`, the window's name in the daemon; `project`, `task`, `starred`, mtm's own records; and the read-only `display`, `session`, `title`, `cwd`, `state`, `harness`, `exited` and the agent's `model`, `effort`, `fast`, `permission-mode` as the settings line reads them): `mtm pane get|list|set|watch|move`, for example `pane get w1 --prop model`, `pane set pane:hub/w1 name=fixer`, `pane move w1 --to hub`. `history.undo` reverts a rename, a star and a move. The agent's settings are read-only props: `pane set-model`, `set-effort`, `set-fast`, `toggle-fast` and `set-permission-mode` stay the verbs that change them, typed into the agent's session. A pane has no `create` or `delete`: `pane kill` closes it (an `actions.json` row `{"alias": "pane.delete", "action": "pane.kill"}` gives the word). `pane rename` and `pane unassociate` run `set` and `move`, and `pane star` (`*`) is an alias of `set` of `starred` with `toggle` (`--value` sets; the old `--starred` still works until the next mtm release, with a one-time notice); `m` on a pane row is `pane.choose-move`. A session's verbs are the same over `id`, `name`, `project` and the read-only `panes` count (`mtm session get|list|set|watch|move`; `m` is `session.choose-move`; `kill` stays). A saved record's verbs are the standard ones over `id`, `name`, `project`, `task`, the recipe (`command`, `env`, `cwd`, `harness`, `model`, `flags`, written by `create` only) and the read-only `window`, `session`, `created`, `updated`: `mtm saved get|list|create|set|delete|watch|move|duplicate`, for example `saved create --name scratch --cwd ~/tmp` (no command reopens a daemon shell). `saved forget ID` is the same as `delete` (the record only; its pane keeps running), and `history.undo` puts a forgotten record back as it was; moving a record moves its live pane with it. `pane.associate`, `session.associate` and `saved.associate --project`, `--task` and `--scratch` are old forms of `move` and `set`, kept for one release.

An action item's verbs are ochazuke's standard ones over its props (`id`; `title`, shown by the read-only `summary` when empty; `why`, `text`, `url`, `kind`; `source`, written by `create` only; `project`, `task`, `pane`, `session`; the marks `read`, `archived` and `snoozed-until`; and the read-only `key`, `state`, `promoted-todo`, `promoted-task` and times): `mtm action-item get|list|create|set|delete|watch|rename|move|duplicate|archive|restore`, for example `action-item list --state all --source gh`, `action-item set ID why="CI failed" read=true` and `action-item move ID --to hub`. `show`, `read`, `unread` and `toggle-read` are the same as `get` and the standard `set` of `read`; `snooze` sets `snoozed-until`; `history.undo` reverts them, and puts a deleted item back as it was. `add` stays the tools' verb: it refreshes the row with the same source and key (else URL), which a `create` never does. On an inbox row `x` and `X` are the standard `archive` and `restore`, `m` is `action-item.choose-move` and `d d` asks "Delete ...? x archives it instead.". `action-item.associate --project`, `--task`, `--dir`, `--pane` and `--scratch` are old forms of `set`, kept for one release.

A Neovim session's verbs are ochazuke's standard ones over its props (`id`, `name`, `project`, `task`, and the read-only `path`, `cwd`, `session`, `window`, `state`, `created`, `updated`): `mtm vim get|list|set|delete|watch|rename|move`, for example `vim list --all`, `vim rename ID --name plans` and `vim move ID --to hub` (a running session's pane moves with it). `vim forget ID` is the same as `delete`: the record and mtm's session file go, never the files edited in it or its live pane. `history.undo` reverts a rename or a move; a forget cannot be undone (its session file is gone). A session is made by opening Neovim (`vim open`), so there is no `create`. On a session row `m` is `vim.choose-move` (the project chooser) and `d d` asks "Forget ...?".

A review's verbs are ochazuke's standard ones over its props (`id`; `status` and `answer`, the review's own; and the pane's, read-only: `pane`, `project`, `task`, `harness`, `session`, `window`, `prompt`, `unread`, `turns`, `output`, `captured`, `created`, `updated`): `mtm review get|list|set|watch`, for example `review list --all` (one row per agent pane, journaled panes included) and `review set ID answer="ship it"`. `review status ID STATUS` is the standard set of `status`; `accept` (`x`), `reject` and `saveAnswer` (`i`) stay their own verbs and run `set`, so `history.undo` reverts them; `s` is `review.choose-status` (the status chooser). A write to a pane mtm did not launch records its review first. A review follows its pane, so it has no `move`, and no `create` or `delete`.

A schedule's verbs are ochazuke's standard ones over its props (`name`, the key; the fields `schedule edit` takes: `prompt`, `when`, `enabled`, `harness`, `model`, `effort`, `fast`, `permission-mode`, `project`, `task`, `dir`, `into`, `pane`, `start`, `end`, `catch-up`, `description`, `kind`, `command`, `drive`, `timeout`; `interval`; and the read-only `source`, `active`, `why`, `running`, `last-run`, `last-outcome`, `last-error`, `failures`, `next-run`, `missed`, and `runs` on `get`): `mtm schedule get|list|create|set|delete|watch`, for example `schedule set --name gh-signals enabled=off interval=15m` and `schedule create --prompt "Sweep the inbox" --when "every 30m"`. A field is written to the row's stored copy (a built-in or `schedules.json` row gets one); `enabled` and `interval` are a configured row's settings (`schedule.NAME.enabled`, `.interval`) and a stored row's own. `show` is the same as `get`, `enable` and `disable` the standard set of `enabled`; `edit`, `toggle` (`e`) and `set-interval` (`i`) run `set`, so `history.undo` reverts them, and undo puts a deleted stored row back as it was. `add` (with `--name` and the form), `duplicate`, `history`, `run-now` and `reset` stay. A schedule's name is its key, so there is no `rename`.

The Settings page (`,`) has three tabs: matomeru, Extensions and ochazuke (`]`/`[` step them; `tab`/`shift+tab` walk every section across them). matomeru's sections are General, Panes, Prompt, Turns, Agent, Notes, Inbox, Schedules (each configured schedule's `enabled` and `interval` under a heading of its name) and Status bar. Extensions holds a section per mounted extension (its `ext.NAME.scope`) and a Status bar section for the segments extensions add. `settings owners` and `settings sections --owner app` list the same from the CLI; ochazuke's `settings.layout` (`tabs+sections`, the default; `tabs`; `sections`) changes how the page lays them out.

An agent in a TUIOS pane can drive mtm over MCP with `mtm mcp serve`; `mtm mcp config claude` prints the entry to add. See [docs/MCP.md](docs/MCP.md).

Module `github.com/unixsuperhero/matomeru`; requires Go 1.26 or newer.

```sh
go install github.com/unixsuperhero/matomeru/cmd/mtm@latest
```

From a checkout, `make install` (or `make build`, which writes `bin/mtm`) passes the version stamp: `-X main.version=… -X main.commit=…` with the tag from `git describe` (`make install VERSION=v0.1.0` overrides it). `mtm --version` prints the version, the commit and the ochazuke version; without the linker stamps it reads the build info the go command embeds.

## Stories

mtm's interactions are [monogatari](https://github.com/unixsuperhero/monogatari) stories: JSON keystroke scripts under `cmd/mtm/stories/<area>/` (areas `panes`, `inbox`, `tasks`, `pin`), played headless against the real App with expectations on what the screen shows. They run in a separate tester build (build tag `monogatari`), `mtm-story`, never installed over `mtm`; a normal build links none of it (`make split-check`: `mtm: 0 monogatari symbols`).

Each session is the real App on a temp database, a temp config directory and a socket nothing listens on, with a faked daemon, launcher, clipboard and opener (`cmd/mtm/storyfakes.go`), so a story never reaches your data, daemon or tuios session. Fixtures: `seeded` (docs/vhs/seed.sh's projects, tasks and notes, two inbox items and two fake panes; a story's `"seed": {"panes": [...]}` replaces the panes) and `empty`. `story` runs before any database opens and ignores `--data`, `--socket` and `--server`. The host keeps its own state under `mtm-story` (user stories in `$XDG_CONFIG_HOME/mtm-story/stories`, recordings in `$XDG_DATA_HOME/mtm-story`), so point those at a temp dir too:

```sh
make story-bin                                   # bin/mtm-story (make story-bin STORY_BIN=/tmp/x/mtm-story elsewhere)
D=$(mktemp -d) && export HOME=$D XDG_CONFIG_HOME=$D/config XDG_DATA_HOME=$D/data XDG_STATE_HOME=$D/state
unset TUIOS_ENV TUIOS_SESSION TUIOS_PANE_ID TUIOS_SOCKET
bin/mtm-story story list                         # the stories by area
bin/mtm-story story run panes                    # headless; non-zero exit on failure
bin/mtm-story story open panes/rename-a-pane     # live, in the real chrome (a name prefix works too)
bin/mtm-story story explore panes --steps 50     # the state explorer, headless
bin/mtm-story story explore panes --watch --delay 500ms   # the explorer's watch page; q stops watching (the runs then finish headless)
bin/mtm-story story help                         # every command: history, keep, replay, trim, verbs, catalog
```

The tests run every story through `host.Test` in the tagged build (`cmd/mtm/stories_test.go`; `-update` rewrites goldens): `make story-test` (`go vet` and `go test -race` with `-tags monogatari`). A UI bug becomes a story before it is fixed; a known gap is a story with `"skip": "gap: ..."`. Editors need `-tags monogatari` in gopls's build flags to see the tagged files.

## Live shell keys

In a live pane every key goes to the program in it, except the `terminal-leader` setting (default `ctrl+a`). After the leader, the app's own normal-mode keys do what they do outside live: the same verb, and the same guard. The palette, settings and pickers open over the pane; closing them (`esc`) gives the pane its keys again.

| Key after the leader | Does | Verb |
|---|---|---|
| `:`, `ctrl+space` | command palette | `ochazuke.palette.open` |
| `,` | Settings (guard `no-modal`) | `ochazuke.settings.edit` |
| `'` | pick a page (guard `no-modal`) | `ochazuke.page.pick` |
| `ctrl+j` / `ctrl+k` | next / previous page | `ochazuke.page.next` / `ochazuke.page.previous` |
| `I` | the Inbox page | `ochazuke.page.open {id: inbox}` |
| `?` | keyboard help: the help tree, with the leader as one row and its keys under it | `ochazuke.bindings.help` |
| `` ` `` | next starred pane, attached live (`s` does the same) | `terminal.starred` |
| `W` | next pane that needs input, attached live | `terminal.waiting` |
| `*` | star or unstar the live pane | `terminal.star` (`pane.star` on the attached pane's row) |
| `\`, `p` | pick a pane | `pane.pick` |
| `P` | pick a project to pin (guard `no-modal`) | `project.pick` |
| `L` | launch an agent | `agent.choose` |

The live-only leader keys stay as they were: `v`/`t` side vim and terminal, `d` close a side or detach, `z` zoom, `o` the other pane, `R` side layout, `w` sides, `j`/`k` next and previous pane, `s` starred, `[` copy mode, `c` context, `f` hints, `N` quick note, `n` new task, `T` todos and `S` all projects. The leader twice sends one leader to the pane. The leader's `?` used to open the leader-only keys modal; that is `terminal.keys` now, from the palette (`terminal keys`). Changing `terminal-leader` moves every row.

Not after the leader: `[`/`]` tabs (`[` is copy mode, and live is the Screen tab), `(`/`)` focus regions, `"` and `@` registers and macros, `/` filter, `<` `>` `=` resize and `.` dot-repeat (they do nothing on the Panes page, which draws its own split and records no repeatable change), and in-component motions (`$ % ^ 0 | ; { }`).

## States reference

The [state/key reference](docs/keys/README.md) describes each measured page,
focus, mode and modal stack, with all bindings including hidden keys.
`docs/keys/states.json` is app-owned reference data outside the story library.
`make states-export OUT=/tmp/mtm-tutorials/export` produces one portable JSON
per state and an index without replaying or building the app. The reusable
hub keymap-outline builder refreshes it in `mode: states`; mtm ships no replay
tutorials.
