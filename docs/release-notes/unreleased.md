# mtm, unreleased

Notes for the next release. CHANGELOG.md is generated by o-inventory; these lines are the hand-written part.

## v0.18.0 (unreleased)

- A fresh daemon restart brings the agents back (owner: "we should have an option to restart/resume agents.  but i would like the upgrady/handoff to be the default....and only let them die with the process on like a restart --fresh or upgrade --fresh"). `daemon restart --hard` is now `daemon restart --fresh` (renamed in one step, no alias), and `daemon upgrade --fresh` does the same stop and start onto the installed mtm; the live handoff stays the default for both, and nothing else ends pane programs (`upgrade --or-restart` still falls back to the fresh restart only when the live upgrade never started). With `daemon.resume-agents` (on) a fresh restart notes the panes running an agent before the stop and, once the daemon has restored them, resumes each on its conversation (the new `pane.resume`, over the daemon's `resume-agent`: the harness manifest's `[resume]` command, such as `claude --resume ID` or `codex resume ID`, typed only while the pane's shell holds the terminal). A pane with no recorded conversation, or whose harness has no resume command (omp today), stays a shell; the answer's `resumed` rows and a notice say which were resumed and which skipped. Off leaves every restored pane a shell, as before. `pane.resume` (`--window`, `--dry-run`) resumes one pane by hand.
- Priority is P0 to P5, or blank (owner: "P0 means like work on this immediately. P1 is like it's very important down to like a P5 which is like not so important and then then normal or not set which should be the default which is kind of like a P6 but it's just visibly on the screen it should be blank"). Tasks and projects take `priority=P0` … `priority=P5` (any case), and `priority=none` (or `""`) clears it; not set reads `""` and shows blank in the priority column, on the Work page and now in the task outline too (both only when `tasks.columns` lists `priority`; off by default). `--sort priority` puts P0 first and not set last; `--where priority=P1` filters. On first open the tasks and projects tables move once, after a backup (`backups/mtm.db.bak-<time>-priority-levels`): urgent is P0, high P1, medium P3, low P5, none not set; any other value is kept. The old words still set the level they became (an undo or a script from before writes P1 for `high`). No setting, binding or saved filter named an old value, so nothing in the config was rewritten. The levels are one list (`internal/work/priority.go`).
