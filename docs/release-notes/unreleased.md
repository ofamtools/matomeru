## faster CLI start (ext-mount-cache)

- Changed: a start mounts the registered extensions with one reload of the sides, the user's actions and the user's bindings (`mountBatch`), not one per extension; a lone mount (register, refresh, sync) still reloads once. A read-only call on a data directory with 16 extensions went from about 0.54 s to 0.20 s together with the items below.
- Added: the mount cache, `<data>/extensions/.mounts.json`. Each tool's registry file holds its whole catalog (about 1 MB, mostly the framework's own verbs and key rows, which mounting never uses); the cache keeps a slim copy per registry file, valid while that file's size and modification time are unchanged, and is rebuilt when it does not read or has another version. The registry files stay the source of truth. Setting `extensions.mount-cache` (default on, Settings -> Extensions -> General) turns it off: every start then reads the registry files in full and writes no cache.
- Changed: the CLI's changed-bin check reuses the registry the start just mounted instead of decoding it again.
- Changed: when mtm runs a command or the MCP gateway (`Options.Headless`), the Inbox rows (`inboxLoad`, lazy.go) load on first need (a row lookup that misses, `--target`). The TUI, `--smoke` and the story host load them in `New`, as before; building them later moved the Panes selection.

## One notifier for inbox items and reminders

- New Slack and GitHub action items notify on any TUI page, from the inbox's startup/five-second reload. `action-item notify-due` uses the same worker headlessly. A persisted first-run baseline suppresses old items; per-item two-minute claims prevent competing processes from sending twice during normal delivery. More than five new items are one summary.
- `notify.channel` defaults to `terminal`; `notify.commands` defaults to the string `"[]"`. Reminders use these senders unless their existing overrides are explicitly set. `reminders.notify` now defaults to empty, meaning follow the shared channel. - `inbox.notify` defaults to `new`, with `off` disabling delivery and notices. `inbox.notify-sources` defaults to `["slack","gh"]`. `action-item add --notify` and the standard `notify` prop bypass only the source filter. `inbox.notify-in-app` defaults to true and holds unread notices without taking focus or opening a modal.
- `notify.failures` defaults to 3 consecutive schedule failures. A failure raises one forced-notification item keyed `schedule-failing:NAME`; success archives it, and a new failure cycle reuses the row. Set the threshold to 0 to stop raising these items.
- Retire the independent `inbox-notify` schedule row before using the built-in notifier. No owner config is changed automatically.
- Real desktop popup permissions and OSC 9 passthrough through tuios remain unverified. A crash between external delivery and its receipt can duplicate a notification after the claim expires.

## Schedules count from the finish

- New schedule field `interval_from` (`interval-from` in `schedule edit|set|create` and the form): `start` (the default; an old row reads as `start`) or `finish`. - The built-in `gh-signals` and `slack-signals` rows default to `finish`.
