# Matomeru on ochazuke: first slice brief

Spec: `~/proj/znbu/docs/outline.md` and its concept outlines (architecture, forms, panes, agents). Reference consumer: `examples/csv` in this repo. The app is a new Go module importing `ofam.dev/ochazuke`; the old app is at `~/proj/matomeru-old`; it and gmtm stay untouched as sources to lift from.

## The slice

One complete workflow, end to end, before any second feature: select a project and task, launch an agent into a TUIOS pane, see the launch delivered, preview the pane, attach live and detach, review the result, save the answer. This is the acceptance check the direction documents agreed on. Nothing else (Slack, GitHub, reminders, MCP) until it works.

## Nouns and verbs (data; handlers are the app's)

```js
define("project",  { verbs: { new, open, launch },                  bindings: { normal: { enter: "open", l: "launch" } } })
define("task",     { verbs: { list, new, open, launch, done, edit }, bindings: { normal: { enter: "open", l: "launch", x: "done", i: "edit" } } })
define("pane",     { verbs: { attach, preview, kill: { confirm: "Kill pane {{label}}?" } }, bindings: { normal: { enter: "attach", p: "preview", K: "kill" } } })
define("agent",    { verbs: { launch: { params: { harness: { enum: registry.names }, model: { source: "harness.models", free: true }, project: { source: "projects.list" } } } } })
define("harness",  { verbs: { list, models } })                       // data only: the registry and the model pick list
define("review",   { verbs: { open, accept, reject, saveAnswer },      bindings: { normal: { enter: "open", a: "accept", r: "reject", s: "saveAnswer" } } })
define("prompt",   framework noun: Readline, insert pinned)
define("terminal", framework noun: passthrough, ctrl+a leader, d detaches)
```

Pages (instances of kind page under app), in tab order: `panes` (pane list → terminal detail, two stops; mtm opens here), `work` (projects list → tasks list, two stops), `review` (reviews list → answer prompt). `}`/`{` move between stops; `ctrl+j`/`ctrl+k` between pages.

## Daemon

mtm talks to its own TUIOS server, `mtm-daemon` (`tuios --server mtm-daemon`, socket `<runtime dir>/servers/mtm-daemon/tuios.sock`), and starts it with `tuios --server mtm-daemon start-server` when nothing listens there (`daemon.Client.Ensure`: probe, start once, poll up to 5 s). The TUI ensures off the loop (`daemon.ensure`, a quiet job, then `panes.refresh`), so it opens at once; the CLI ensures before dispatch; `--smoke` never does, and without an explicit `-data` it renders a fresh temp database and names a socket nothing listens on (`smokeOptions`). A server that cannot start is the panes page hint and the footer error (`daemon mtm-daemon not running: ...`) and the rest of the app keeps working. `-server NAME` (or `MTM_SERVER`; the flag beats the env, the env beats `mtm-daemon`) picks another server; `-server default` is the user's own daemon (`TUIOS_SOCKET` or the runtime dir), which mtm only probes and never starts. An explicit `-socket PATH` wins over both; `TUIOS_SOCKET` alone does not, so mtm run inside the user's tuios still uses `mtm-daemon`. Panes mtm launches live on that daemon and are attached through mtm, not through the user's main tuios.

## Harnesses

A harness is data, not code: `internal/harness` holds `Harness{name, command, modelFlag, models, prompt: "send-text" | "arg", ready: {state | pattern, timeoutMs}, env, attach: "mention" | "paste"}`, the built-ins `claude` (`claude --model opus|sonnet|haiku`), `omp` (`omp [--model provider/id]`, any model) and `codex` (`codex [--model m]`, any model), all typed into once tuios reports them `idle,done`. `<config>/harnesses.json` (or `-harnesses PATH`; the config directory is below) is a JSON array merged by name over the built-ins: an entry naming a built-in changes only the fields it gives (`{"name": "omp", "command": ["omp-dev"]}`), any other adds a harness, and a bad entry (no name, empty command, unknown prompt mode, unknown field) stops startup with the file and the reason. Every launch is one flow (`harness.Launcher.Launch` over a three-call `Driver`): `LaunchWorkspace`, `new-window` running the harness's argv (`env K=V` first when it sets env, the model flag when a model is given, the prompt last for `prompt: "arg"`) in the project's tree, named from the task; then, when there is a prompt, `wait-for` the readiness probe (or a fixed delay when it has none) and `send-text` with submit. A pane that is not ready in time keeps its prompt unsent and says so in the panes header. `pane.new` is the same flow with no harness and no prompt. `start-agent` is not used: it would be a second path, for the harnesses tuios knows, beside one that runs any argv. The harness of a launch is its `harness` argument, else the project's `settings.harness`, else `claude`; the model is checked against that harness's models (free text when it lists none). The review row and the launch error name the harness; `mtm harness list` prints the registry. `attach` is how a harness takes a file attached in the prompt box (ctrl+v pastes an image as `[image N]`): `mention` (the default; `claude` and `omp`) sends each as `@/abs/path` in the text, read at submit; `paste` (`codex`, whose `@` is only a file search) types each path as a bracketed paste of its own before the text. A queued prompt always carries `@` mentions, since tuios types it later as one paste. This is the last time harness code is written in the app: a new harness is a JSON entry, and the package imports nothing from the app, so it can move to its own repository as is.

A harness profile also says how a running session's settings change: `settings` rows by name (`model`, `effort`, `fast`, `permission-mode`), each `{values, command: "/model {value}"}` typed into the pane and submitted, or `{key: "BTab", cycle: [...], screen: {mode: "text the footer shows"}}` pressed until the pane's screen shows the value, plus `contextWindows` by model glob. A file row replaces a built-in row by name and `null` removes one. Built-ins (read from the installed versions, 2026-10-28): Claude Code 2.1.312 `/model`, `/effort`, `/fast`, and shift+tab through its permission modes; omp 18.13.0 `/switch` (session only), `/effort`, `/fast`; Codex 0.162.1 none (its `/model` and `/permissions` are pickers without an argument). The Turns tab draws the agent's settings line under the prompt box (`Opus 5.5 · effort medium · fast off · bypass · ctx 32% · $1.20`), each value from the session's own log first (`turns.Live`: Claude's transcript, omp's session log, Codex's rollout), then tuios's metadata, then the launch flags marked `(at launch)`; a narrow panel drops cost, fast, effort first. Each field is a `pane-setting` row: j from the box's last line reaches it, h/l walk it, enter opens a chooser of the profile's values with the current one marked, esc goes to the pane row. The pane verbs `set-model`, `set-effort`, `set-fast`, `toggle-fast`, `set-permission-mode` (a value, or a chooser), `settings` (the fields and their sources) and `settings-line` reach the same from the palette and the CLI. A change is typed when the agent rests, queued through tuios's delivery queue while it works (a stepped key is refused then), refused while it waits on the person, and asks first over a draft in the prompt box for that pane; the log is read again after it and a notice says what the harness now reports.

A harness profile says how the prompt box writes to its panes: `promptBox: {deliver: "queue" | "send", submit: "enter" | "none"}` (beside `session`; merged by field, `null` removes it; the key is not `prompt`, which is the first prompt at launch). `deliver: "queue"` (every built-in, and the default) is an agent's box: its send (a steer while the agent works), queue (tuios `queue-prompt`) and interrupt modes, never typed over a question the agent waits on. `deliver: "send"` is a terminal's: one `send-text` that types the text as one paste (bracketed when the program turned bracketed paste on, so a shell holds a multi-line text whole) and then presses the program's Enter, or with `submit: "none"` leaves it typed; the box has no other mode, so ctrl+t stands aside. A pane with no profile takes the agent box when tuios reports an agent in it, else the terminal box (`harness.TerminalPromptBox`). Every live pane gets a box below the Turns tab's turns and below the Screen tab's screen (while no live terminal or copy mode is drawn); `i` on the pane row or a turn focuses it and stands aside on an exited pane (availability on `pane.prompt` and `turn*.prompt`). Opt out with `prompt.on-terminals` (terminals) and `prompt.on-screen` (the Screen tab); both default on.

A harness profile also says where the harness records the session a running agent writes now: `session` (`internal/harness/session.go`, read by `internal/locate` on every listing, off the loop). tuios reports the id it first heard, which goes stale after a `/clear`, a resume, or when the pane's agent only attaches to a session another process runs (Claude Code's background daemon). A record is a file, `files` a glob (`~`, `${VAR:-default}`, `{tty}` the pane's terminal), `format` `json` (fields are keys) or `lines` (line numbers). It is the pane's when its `pid` is running, started when `start` says (a reused pid is not trusted) and one of `env` in its environment is the pane's window id, or when `{tty}` names it and `process` runs on that terminal. The transcript is the `path` field or the `transcript` template (`{session}`, `{cwd}`, `{cwd_slug}`); `session` or `sessionPattern` gives the id. A record the pane holds with a transcript replaces tuios's id (kept as `reported_session`), and a pane tuios reports no harness for takes the record's. A pane with none, whose reported id has no transcript, takes the one running session no listed pane holds that started in its folder; two or more are a notice (`session_note`), never a guess, and another unresolved pane of the harness in the folder means nothing is taken. Built-ins: `claude` reads `${CLAUDE_CONFIG_DIR:-~/.claude}/sessions/<pid>.json` (`sessionId`, `cwd`, `procStart`; Claude Code rewrites `sessionId` when the process changes session) with `TUIOS_WINDOW_ID`/`TUIOS_PANE_ID`; `omp` reads `${PI_CODING_AGENT_DIR:-~/.omp/agent}/terminal-sessions/<tty>` (line 1 the folder, line 2 the session file) while `omp` runs on the terminal; `codex` has none. ps runs at most once per 5 s; `pane.refresh-turns` asks again.

## Subagents and notifications on the Turns tab

A Claude Code spawn call (`Agent`, `Task` before 2.1) is a step titled `agent <type>`: description, state (running, done, failed, stopped), background or foreground, duration and tokens, and in its body the model, the brief's first lines, the result and the transcript's path (`transcript missing` when it is on no disk and in no log). `internal/turns/agent.go` reads it: the call's input, the result's `toolUseResult` (a background launch is `async_launched` and keeps running; a foreground one ends with `totalTokens`, `totalDurationMs`, `totalToolUseCount`), the session's `<session>/subagents/agent-<id>.meta.json` (type, `spawnDepth`, `parentAgentId`, `toolUseId`) and, for an older log, its `isSidechain` records, which are the agent's and never end or touch the parent's turn.

A `<task-notification>` (promptSource `system`) is an event, never a prompt: a compact, muted, closed card `⤷ <description> · finished · 20m43s · 205k tokens · 94 tool uses · from “<spawning prompt>”` whose body is the agent's result as steps, then what the agent did about it. It links back to the spawning call by `tool-use-id` (else the agent id), whose step shows the same state. One that lands while a turn runs (a user record or a queued attachment) is a card of its own after that turn's, and a message the person wrote beside it stays the real prompt; repeats of one task (`waiting on its own background work`, then `finished`) fold into its first card, which shows the latest state. Bash, monitor and workflow notifications are cards too.

Opening an agent step (or stepping onto it) reads its own log off the loop (`turns.AgentLogs`: cached by mtime and size, read from its end when over 1 MiB, a running one again once per listing); its turns follow as steps nested one level, each title led by `│ `: brief, thinking, text, tool calls, answer. Nesting stops at 2 levels (`spawnDepth` 2 shows its call; o opens its transcript). The tree style draws the same as rows. Verbs on an agent step and on its notification's card: `open-transcript` (`o`), `copy-brief`, `copy-result`. Nothing reads a subagent's log until its step opens: 70 subagents add no file reads to a fill.

## Off-loop work (the delivery contract)

- `agent.launch` → `Pending(work)`, accumulate; its completion refreshes the pane list and shows up in `jobs.list` (the status rail renders that list).
- `pane.preview` → `Pending(work).Replacing("preview")`; a newer preview cancels the older.
- Attach: `AddTerminal(id, Parent(panesPage), stream)` with the daemon's `stream-pane`; the terminal noun's leader contract handles detach. Size lease released on `Close`.
- A subagent step that opens → `turn.read-subagent`, `Pending(turns.AgentLogs.Read)`; its completion rebuilds the shown turns.
- Everything else runs on the loop and returns `Done`.

Copy mode: `ctrl+a [` from live keeps the pane attached; `esc` or `q` restores that live terminal, including a side pane or zoom. Entering from the pane list returns to the list instead. `i` or `enter` always goes live. A visible copy cursor tracks motions before selection and marks the active endpoint during selection; the pane keeps running.

## A launch ends with the pane on screen (owner rule)

`agent.launch` and `pane.new` normally finish on the panes page with the new pane attached. An explicit launch outside the pin attaches with `outside pin: PROJECT`, without widening the list or changing the pin. If the pin changes while a launch is running, completion records its review and only notifies; it does not navigate. Ownership is captured before the job and saved immediately after creation, before readiness waits or listing. A failed listing retains the created pane; a failed ownership write reports the failure and leaves the pane available for reassignment.

## Project pin and launch ownership

`project pin ID` persists a project-only pin; `project unpin` persists an empty pin. `P` opens the pin picker from every page in normal mode. The title shows `Matomeru · PROJECT`. `S` (`scope all`) widens the current process's lists without changing the pin. Colours follow the pin: pinned draws the owner's theme, show all the same theme with an orange accent, no pin ochazuke's mono; errors and muted text keep their colours. `J`/`K` scroll the page's detail (Panes' tabs, the Work detail, the note body, the opened review) while the list keeps the focus; counts work (`20K`), and Screen, Activity, Transcript and a review's output open at their end. `,` opens the framework's Settings page (`settings edit`) from every page in normal mode, and `q` or `esc` goes back to the page it came from; mtm declares `edit-debounce`, `refresh-interval`, `default-harness` and `panes.group` among others, kept in `settings.json` in mtm's config directory beside `bindings.json`, `harnesses.json` and `dirs.json`. `mtm config reload` (ochazuke's `config.reload`) reads them all again and prints the problems: after the framework's files, `harnesses.json` (the registry and the harness parameters' choices; the `default-harness` setting's choices stay as declared at startup) and `dirs.json` (the bases list, and a rescan when one had run); a bad file is a problem naming it and keeps the old configuration. The extension registry is not part of it (it is data the extension verbs write, synced when a page opens). `task list`, `pane list`, `session list`, and `review list` accept `--all`.

Generic `agent launch` and `pane new` use explicit task/project arguments, then the pin, never a merely browsed project, cwd, or last launch. `project launch`, `task launch`, and explicit CLI `--target` actions use the addressed record. Task ownership wins conflicting project arguments. Other record creation continues through `resolveOwner`: explicit arguments, selected record, pin, unassociated. Unknown associations remain unassociated with a notice.

`project → session name` remains a pure slug function; there is no session picker. `--scratch` overrides all ownership and confirms `no-project` for agents or `mtm-only` for shells. Unassociated launches start in home. A project's missing default directory also falls back to home with a notice. Every launch and attach records directory recency.

Pane ownership lives in the existing `assignments` table keyed by window id. Session ownership lives in `session_owners` keyed by stable session id, not its display name. A pane without an assignment inherits its session; an empty assignment explicitly remains unassociated. `pane associate --target pane:SESSION/WINDOW --project ID`, `session associate --target session:ID --project ID`, and `task associate --target ID --project ID` reassign records; `--scratch` removes ownership. Reviews keep launch-time ownership and show the pane's current owner in their detail.

On first open, existing assignments are preserved and missing pane assignments are imported from reviews once. The old `active/singleton` task pin becomes its project; otherwise legacy `launch_state/last` seeds the pin once. Subsequent explicit unpinning never reseeds it. The old last-launch API and cwd ownership inference are removed.

## CLI extensions

`mtm` is an oden app (`ofam.dev/oden`, at ~/proj/oden; a local `replace` in go.mod until it is tagged). Any executable `mtm-<sub>` on PATH is the command `mtm <sub>`, run with the remaining words, mtm's stdio and `ODEN_PARENT`/`ODEN_ROOT` set, so a third party adds `mtm web` by installing `mtm-web` without touching this repo. After the global flags the first word resolves by exact name, alias or unique prefix to: oden's builtins (`mtm help`/`-h`/`--help` lists every command with kind, source and shadowed claims; `mtm commands` prints the catalog as JSON; `mtm which WORD` prints what a word resolves to), then the runtime's nouns (`mtm ta launch` is `task launch`; the shell also takes a unique verb prefix, `mtm bind li`), then `mtm-<sub>` bins; no word runs the TUI, an unknown word reaches the NOUN VERB shell, an ambiguous prefix lists its candidates and exits 1. A noun always wins over a same-named bin, which help shows as `shadows external PATH`. After its own `mtm-<sub>` bins mtm also discovers the family's `o-<sub>` tools (`oden.WithPrefixes("o")`): `mtm ai` runs `o-ai` unless an `mtm-ai` is on PATH, which then wins and lists `o-ai` as shadowed. `o-proj` is hidden from that discovery, and `proj` is an inline short spelling of mtm's `project` noun. mtm has no bare-name lookup. Nesting follows the name: `mtm-ai` built on oden resolves `mtm-ai-skills`, so `mtm ai skills` runs `mtm-ai skills` runs `mtm-ai-skills`; a descendant never makes a prefix ambiguous (`mtm a` is `ai`, not `ai` or `ai-skills`). The adapter is `cmd/mtm/oden.go`.

Docs come from o-md (`~/proj/o-md`), an extension like o-ai or o-git, not from mtm's code: `mtm extension register md` (its bin `o-md` on PATH; the Extensions page lists it as available) mounts its Docs page as a tab after mtm's pages (mounted pages follow registration order; mtm cannot place a tab after Notes). The page is a split of o-md's `doc` rows (the Markdown files under o-md's `docs.roots` setting, `o-md settings set docs.roots ...`, plus the pinned project's directories) beside a `markdown` detail: mtm registers ochazuke's markdown detail kind (`markdown/cliview`, `extension_context.go`), so the selected file is the inline editor, committed on change, and the doc's verbs (palette `md.doc.*`, or `doc.*` while no other extension has a `doc` noun) act on it from inside the editor too. Every extension exec carries `MTM_PROJECT_DIRS`, the pinned project's directories (`:` between; empty without a pin). A verb parameter naming mtm's `pane` noun that a call leaves out opens mtm's pane chooser (`md.doc.send-notes`). `S` stays `scope.all`: mtm drops an extension's key row on a key it binds app-wide, so send-notes has no key there (palette, or a row in `bindings.json`).

`o-proj` (`o proj`) moved to its own repository, `~/proj/o-proj` (ofam.dev/o-proj). It keeps the family's repositories on disk (a manifest `$HOME/hub/repos.json`, hub links, clone, sync, status) and no longer opens mtm's store. It is a different thing from mtm's `project` noun (a work context) and the two meet only through each other's command line: `o proj new` creates a work project with `mtm project new NAME --dir DIR` after checking `mtm catalog` for `project.new` and `mtm projects directories` for a project that already has the directory; mtm reads `o-proj list` as a known-directory source. `mtm proj` is the inline short spelling of `project` (`cmd/mtm/oden.go`), and mtm's discovery hides `o-proj`. `project new NAME --dir PATH` attaches PATH and makes it the default; `projects directories` prints every project's directories (resolved like known directories) as rows `{id, label, data: {directories, default}}`. Projects o-proj registered before the split keep their rows, directories and `origin` field.

`o proj new NAME --family` (short form `-o`) explicitly requests the o/oden family symlink, `$HOME/hub/o/NAME -> ~/proj/NAME`. Family linking remains enabled by default; `--family=false` (or `-o=false`) skips it. `--hub DIR` still selects another hub and `--hub none` still skips linking, even with `--family`. The noun spelling `o proj project new NAME --family` exposes the same boolean in its catalog; JSON callers can pass `"family": false` to skip.

The `no project (unassociated)` project-list row opens unassociated tasks, and `--target` can reveal those tasks. `task list` includes unassociated records. Empty project names and task titles display as `untitled`.

Project creation and project/task/note editing commit on change: a new record is written when the editor opens (an empty title saves), typing in any field is written about 400 ms after it pauses and at once when the field, insert mode or the editor is left, and a change in normal mode (an undo) is written at once. Project fields are name, theme color, glyph, harness, and preset; a project without a glyph draws `◆` (the record is not rewritten). Task fields are title and status. There is no save key: `enter` in a one-line field and normal-mode `q` or `esc` leave the editor, never discarding; normal-mode `u` undoes the field's text and the undo is written. Normal-mode focus navigation moves between fields. Moving between stops or pages does not prompt. No draft files are written; drafts left by an older mtm still list and open. Saving an existing record preserves its directories, ownership, and other metadata. Selecting a task shows its detail; `enter` or `i` opens its editor (`l` opens the detail).

`project directory PATH --target ID` attaches a directory without creating it. Omitting `PATH` opens the cached known-directory chooser. The chooser merges all project trees, TUIOS directories, and repositories under the configured project base directories. Its search field applies fuzzy filtering without rescanning. `browse…` opens ochazuke's path picker; `ctrl+y` selects the current directory, including an empty directory. After the picker returns, Enter attaches the path. A typed missing path also attaches and appears as missing in project detail.

`project default PATH --target ID` sets an attached directory as the default. The first attached directory is the initial default. Paths can belong to several projects; project detail names the other projects. `internal/work.Store.AddTree` and `SetDefaultTree` own these changes; `project new --dir` uses them too (which is how `o proj new` creates a work project).

Project bases are read from `<config>/dirs.json`. The config directory is `-config DIR`, else `MTM_CONFIG_DIR`, else the directory of a non-default `-data` (a copy of the database keeps its config beside it, so tests and reviews never touch the owner's), else `$XDG_CONFIG_HOME/matomeru` or `~/.config/matomeru`. `MTM_PROJECT_BASE_DIRS` overrides the file. `dirs bases` reports the effective sources; `dirs add-base PATH --depth N` and `dirs remove-base PATH` update the file. The default depth is one. Repository discovery follows symlinks and deduplicates real paths. Missing bases appear in the chooser footer. Recency comes from `dir_recent`, with TUIOS activity imported only for paths without recorded usage.

Notes have their own Notes page, reached with the framework page navigation. `n` creates a draft, Enter opens the note as ochazuke's inline Markdown editor (the markdown Doc: a line cursor, `i a I A o O` edit in place, `x` toggles, committed on change), and `i` on the note row edits the record. The editor is lane B's shared right-panel editor on Work: note text is multiline, Enter inserts a newline, Escape leaves insert mode, and normal-mode `s` saves or `q` cancels. Whitespace and empty bodies are retained. Moving away keeps the draft; reopening with `i` or opening a new draft row restores it after restart.

CLI: `note new TEXT [--task ID] [--project ID]`, `note list [--all]`, `note view --target ID`, `note edit TEXT --target ID`, and `note associate --target ID [--task ID|--project ID|--scratch]`. Omitted text opens the shared editor; an explicit `""` saves empty. New notes capture `resolveOwner` once; task ownership wins over a conflicting project, and CLI creation never reads TUI selection. The list and saved preview use `inScope`, including task-only legacy notes whose project is inherited from their task. Association changes ownership without changing the saved body or losing an unfinished draft.

`internal/work/notes.go` declares no migration: the existing notes table keeps owner `notes`, key `id`, version 1. Reads ignore unknown legacy fields; saving preserves them, including provenance. Project and task details now list their scoped notes.

Integration is complete. Pin changes clear out-of-scope editors, details, directory paths, and pane previews. Unfinished edits remain on disk. Preview and review completions check the pin version before publishing output. A review cannot capture a pane whose current owner is outside the pin. The project picker and known-directory chooser remain global by design; project details and task lists do not expose another project's contents while scoped.

`project delete --target ID` and `task delete --target ID`, or normal-mode `d d` on their rows (notes too), show a confirmation with separate counts for affected tasks, notes, pane owners, session owners, and reviews. `--yes` accepts through the framework CLI. Deletion preserves child records and unknown JSON fields, clears the deleted owner, and records `former_project_id` or `former_task_id`. Deleting a task preserves its children's effective project. Deleting the pinned project clears the pin. Related drafts lose the deleted owner without losing their text; the deleted record's own draft is removed. Neither directories nor live panes are deleted.

CLI preparation opens neutral Work focus before dispatch. Generic launches therefore use the pin even when the first project row belongs to another project. Explicit `--target` actions still address their record. Integration verification used an isolated ten-step run covering editor acceptance, compatibility-copy changes, and final checks.

Saved-pane metadata uses `saved_panes` with owner `work` and key `id`. Confirmed launch requests use `pane_recipes`, owner `work`, key `window`. Neovim metadata keeps the legacy `vim_sessions` declaration with owner `vim`, key `id`, version 1. All three retain project and task ownership. Deleting an owner orphans these records without removing panes or session files. Vim reads and writes preserve unknown legacy JSON fields.

The Saved page lists shell and agent recipes through the project pin. `saved save PANE [NAME]` records a live pane, including its argv, model, flags, launch directory, and owner. Re-saving the same pane retains the record ID. `saved list --all` widens the CLI list without changing the pin. `saved reopen ID` attaches a live pane or launches the recorded argv again, without consulting changed harness defaults. `saved rename ID NAME`, `saved associate ID --project PROJECT` or `--task TASK` or `--scratch`, and `saved forget ID` change records without killing panes. Dead panes reopen in the current owner's project session or the shell/agent scratch session. Reopen restores the launch recipe, not an agent's conversation history.

On a pane row, `w` saves its recipe. Saved rows bind `w` to save, Enter to reopen, `r` to rename, `m` to move (the project chooser), and `d d` to forget (confirmed). The list refreshes when the page opens. Renames commit on Enter. These keys do not run inside a live terminal or editor. The daemon does not expose exact launch argv for every external pane, so saving one can return an explicit unsupported-recipe error. A shell launched with daemon-default argv remains a daemon-default-shell recipe.

The Vim page lists Neovim records through the same pin filter. `vim open [PATH]` launches real `nvim` in a daemon pane with its own RPC socket. No path opens Neovim without a file; `--scratch` forces unassociated ownership. A directory argument sets the working directory. The initial session snapshot lives beside the database in `vim-sessions/ID.vim`. `vim save [PATH] --id ID` runs `:mksession!` through RPC and reports Neovim errors. Saving does not write edited buffers. `--pane PANE` can select the editor instead.

`vim reopen ID` reuses the live pane by stable ID, including after a session rename. Otherwise it starts `nvim -S SESSION_FILE`; records and saved layouts survive mtm restarts. `vim forget ID` removes its record and the mtm-owned session file, never edited files, explicit session paths, or live panes. Unmarked legacy session files are retained. A legacy live editor without a recorded RPC address must be closed and reopened before `vim save` can control it.

Vim rows bind `n` to open, `w` to save the session, Enter to reopen, and `d d` to forget (confirmed). The empty list supports `n`; the list refreshes when the page opens and with every pane listing. Live Neovim receives its own keys; `ctrl+a d` detaches through the framework terminal.

Live panes support `ctrl+a v` (side Neovim) and `ctrl+a t` (side shell). Each is created once per parent in its current daemon-reported directory, with its recorded launch environment, session and owner. Switching replaces the sidebar contents without restarting either process. `ctrl+a d` hides the front companion and restores the other if shown; another hides that companion; with neither shown it detaches the parent. `ctrl+a z` zooms the focused terminal. The detail splits horizontally when it has at least 80 columns and stacks otherwise.

`pane side vim|term|list --target PANE` exposes the same companions through the CLI. Persisted `companions` links retain window, parent and kind across restarts; shown/front state is memory-only. Companions are omitted from the Panes rows and shown as `v`/`t` badges on their parent. Parent and session kill refuse while linked processes remain alive, including hidden companions; close the shell or Neovim normally, then retry. App quit never refuses for companions: they keep running in the daemon, and the next start reattaches the live ones to their parents (`ctrl+a v`/`t` shows the same process) and drops links whose window has gone. Quit while a companion is still opening waits for its launch to finish, so its link is saved, then exits; no new companion starts meanwhile. Parent process exit releases surviving companions as ordinary rows without discarding ownership. Exit checks distinguish retained daemon windows from running processes.

Pane list grouping: the `panes.group` setting picks the Panes tree's levels: `project-pane` (the default: projects, then their panes from every session), `project-session-pane` (projects, sessions, panes), `session-pane` (sessions, then panes) or `flat` (panes alone). Sessions stay in the data, their rows and verbs shown wherever the grouping has them. While a project is pinned the pin is the project level, so it is dropped: `project-pane` lists the pin's panes flat, `project-session-pane` and `session-pane` its sessions then panes, `flat` its panes; the attached pane outside the pin keeps its `outside pin` group in every grouping. Needs input sorts first in every grouping, and groups with one first. `panes.group {group}` sets it and `panes.cycle-group` (`delta -1` goes back) steps through the values, from the palette or the CLI; no key binds them (`z`/`Z` are kept for ochazuke's generic grouping).

Pane row markers: a pane row starts with a three-cell gutter, one cell per slot and blank when its marker is off, so the slots line up down the list: `★` when starred, `◧` while a side Neovim or shell is open, then its agent's state glyph (`●` working, `○` idle, `✓` done, `✗` errored, `?` needs input, `×` exited; blank for a shell). Its name is followed by `W` while prompts wait in the pane's delivery queue (list-agents' `queued`, no count; it goes when the queue empties, on the same refresh as the state). Project and session rows carry no gutter (the tree indents them apart). Markers are glyphs and letters, so mono and `NO_COLOR` read the same. Colour is the theme's, through ochazuke tones (R5.14), never a colour in mtm: the state glyph and the state column carry `state.working`, `state.needs-input`, `state.done`, `state.errored`, `state.idle` or `state.exited` (a shell none), the star `marker.star`, `W` `marker.queued`, and `◧` `marker.side` (no built-in theme draws it; plain until set). A user recolours them under a scheme's `"tones"` in `themes.json`, or with a tones-only entry named after a built-in theme (`{"dark": {"tones": {"state.working": "#5FAFD7"}}}`). With no pin mtm draws ochazuke's mono theme, where a tone shows its attributes alone (bold, dim). `W` the marker is not `W` the key: the header's `W next` jumps to the next `?` (needs input) row, not to a `W` row.

Pane refresh closes daemon windows whose processes have exited and removes their rows. If the live parent exited or disappeared, refresh detaches it, releases both terminal streams and size leases, and restores normal-mode list navigation. Surviving side processes become ordinary pane rows; a failed listing does not detach a live terminal.


Known gaps:

- Framework: `execute` (runtime.go) rejects a target that is not an instance and has no resolver hook (the app's `reveal` covers it); `bindings.list` is focus-scoped, so an app-wide listing is one `--target` per stop; history is not persisted.
- App: there is no "review this pane" verb; a job's rail label is its verb (the framework's `JobInfo` has no label), so the harness shows in the launch error and the review row, not in the rail.

Key map (2026-10-26): one meaning per key on every page. `d d` deletes, kills, forgets or removes (confirmed where `u` cannot undo it); `n` creates; `L` launches an agent through the harness chooser on the project's harness (`L enter` is the fast path; `l` opens); `i` edits (the record editor, a review's answer; `enter` on a Work task row opens the record editor too); `r` renames; `x` marks done or accepts; `s` opens a status chooser (review reject is there); `w` saves a record; `m` moves (`pane`, `session`, `task`, `note` and `saved` `associate`, each the one move verb of its noun); `q` and `esc` close an editor, the outline or a modal; `Q` records a macro (mtm moves the app's `q` macro rows; ochazuke's default stays `q`); `a` is unbound. On a project row `c` attaches a directory and on Panes `W` jumps to the next pane that needs input. `TestBindingsFollowTheKeyMap` checks it.

No pin (owner, 2026-10-26): no pin means all projects on every list, `T` included (its all view, opening on the no project branch so `o` adds an unassociated todo). On Work the projects list shows every project and the tasks follow the selected row, pinned or not; selecting a project never pins it (`P` does).

Projects and tasks convert (owner, 2026-10-28). In the task outline (`T`, the all view `S`) `tab` on a project row (`outline-project.demote`, also on a project's own outline root) makes the project a task of the project listed above it: the task, named as the project was, goes last at that project's top level; the project's tasks become its subtasks in their order and nesting; every row that named the project alone (notes, context items, inbox items, reviews, saved panes, pane recipes, Vim sessions, pane and session owners, launch state) names `{parent, the new task}` and every row that named one of its tasks names the parent with that task; its directories join the parent's (identical paths once, the parent's default kept, or the project's when the parent had none); a pin on it moves to the parent, and a project's outline follows it there; then the project row is deleted. The first project is refused (no project above it). `shift+tab` on a task directly under its project (the guarded `outline-task.outdent`, also `outline-task.promote`) makes the task a project listed right after it: its subtasks become the project's tasks; rows owned by the task name the new project alone, rows owned by a subtask the new project with that subtask; and no directory is lost: the launch directories of the panes it owns (pane recipes), its saved panes' and Vim sessions' working directories, its context items of kind `dir`, the working directories its context items were seen in and its journal entries' working directories (the task's own rows before its subtasks', newest first) become the new project's directories, the first its default. The project it came from keeps its own. Deeper tasks outdent one level as before. Each conversion is one store transaction (`work.DemoteProject`, `work.PromoteTask`) and one step on the outline's undo stack: `u` puts back every row it wrote with the same ids and owners (restoring only the fields it changed on a row edited since), `ctrl+r` writes it again with the same new id. `project make-task --target ID [--parent ID]` and `task make-project --target ID` do the same from the palette and the CLI, without the undo step. `J`/`K` on a project row stay refused (projects keep their creation order) and stay listed in `?` help; `tab` on "no project" stays refused.

Task image attachments: in Tasks (`T`, or a project's/task's `O` outline), `ctrl+v` while editing a task uses the prompt box's clipboard reader and `[image N]` chips. Clipboard images are saved as PNG beside the database under `attachments/task-<id>/`; copied PNG, JPG/JPEG, GIF and WebP files retain their original paths. Copied non-image files become `@path` mentions; ordinary text stays text. Project rows do not take attachments.

Deleting a chip removes that attachment; undo restores it. `task-outline.detach` removes the numbered image (`n`), the only image, or opens a chooser. Cancelling the chooser leaves the attachments unchanged. The outline still writes edits after its typing pause or when leaving the line: Escape saves and closes, never discards a draft. A clipboard read finishing after that editor closes cannot attach to another task or a reopened editor for the same task.

Saved task titles contain the prompt's absolute `@path` mentions (quoted and escaped where necessary), not transient chip numbers. Reopening Tasks restores the chips, including after restarting mtm; other task views and task consumers retain the file mentions. Removing an attachment does not delete its file, matching prompt attachment lifetime. `tasks.image-attachments` defaults to `true`; set it to `false` to show raw mentions and disable image paste/detach in Tasks. The setting takes effect the next time the outline opens.
