# Task outline: friction list (2026-11-11)

Source: about 40 minutes of driving the live task outline (`O` on a project, `T`) with `~/hub/tools/tui-drive` against a copy of the real database (mtm at main, ochazuke v0.122.0), after reading the owner's open tasks in the `outline` project ("add more statuses and spcial char...", "reorder", "add notes", "include context from context picker") and the global task list ("archive as a status that hides in the main list", "need to be ale to add priority", "shorthand names/ids"). The owner's "reorder" task has no body, so reorder was read as: put tasks in the order I want, fast, wherever they are.

Operations tried: add (`o`, `O`, `n`, enter chains), rename (`i`), reorder (`J`/`K`, `3J`, `V j J`, at both edges, on a parent, on a child), indent/outdent (`tab`, `shift+tab`), nest, status (`x`, `s`), archive (palette), filter (`/`), undo (`u`), yank/delete/put (`d d`, `p`), move to another project (`m`, palette), help (`?`).

Ranked, worst first. "Fixed" names the commit lane (see the hand-back for shas).

1. **Reorder is one step at a time and stops dead** (reorder task). `J`/`K` swapped with the next sibling only: no count (`3J` moved one row), no way to the top or bottom (`K` five times), nothing over a selection (`V j J` just moved the cursor), and a child could never leave its parent by moving: `K` on the first child (or `J` on the last) did nothing, silently. The only other way to reorder across a parent was `d d` then `p`. Fixed in ochazuke (library: outline focus, keys and counts are its): `outline.move` takes `count` and `to` (`first`, `last`), setting `tree.move-spill` (default on), rows `g K`/`g J`, `J`/`K` in visual-line over a selection (block, one undo step). Consumer matomeru gets it with the ochazuke bump.
2. **A task cannot be moved to another project from the outline.** `m` is "move" on every other row; in the outline it was unbound, and the palette's `task choose-move` failed with `unknown operation "outline-task.associate"`. Fixed in matomeru (task state lives here): `outline-task.choose-move`, key `m`.
3. **Task verbs do not reach the outline row.** From the palette, `task archive` asks "Choose id" and lists every task instead of acting on the row under the cursor; archiving from the outline had no verb or key. Fixed in matomeru: `outline-task.archive-task` (`A`) and `outline-task.restore-task` (`X`), over a selection too.
4. **A spill to the top level was an error, not an edge.** With moves that go out of the parent (item 1), `K` at a project's first task would otherwise have shown "A task stays under a project: change refused". Fixed in matomeru: `Tree.Refuse` for a task moved to the top level, so it is a quiet edge.
5. **Reorder keys are hard to find.** The footer cuts after five hints and the intro lines say "o add · tab nest · shift+tab out · x done · s status": `J`/`K` (and now `g J`/`g K`) are not mentioned. Not fixed (hints come from bindings; the modal footer is one truncated line).
6. **Status takes `s`, a picker, a pick, enter.** Four steps for a common change; `x` only toggles done. "add more statuses and special char to fill in the checkbox brackets" is the owner's open task. Not fixed.
7. **`i` on a row opens it with the title selected**, so typing replaces the title (the `rename.select` setting, default on) while the intro says "i renames": fixing a typo needs `end`/arrows first. Not fixed (it is a setting already).
8. **Undo does not cover a move to another project** (the move leaves the tree; the store's own history has it: `history-entry.undo`). Not fixed.
9. **Visual selection and `m`**: one `m` moves the cursor row only. Not fixed (the project chooser needs a Subjects path for rows that are not task instances).
10. **A new blank row draws its `[ ]` at the far right** until typed into. Cosmetic. Not fixed.
11. **`?` opens a 96-row help over the outline**; `q` closes it, but the first keys after opening it go to the help, not the outline. Not fixed.
